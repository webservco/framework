# Internationalization

`\WebServCo\Framework\Libraries\I18n`

Translations through [gettext](https://www.php.net/manual/en/book.gettext.php). The library switches the locale and text domain to the current language and gives you the `__()` and `___()` functions.

- Implements: `Interfaces\I18nInterface`
- Requires: `ext-gettext`, the locales installed on the server (`locale -a`)

---

## Instantiation

In controllers, repositories and forms: `$this->i18n()`. Elsewhere: `\WebServCo\Framework\Helpers\I18nLibraryHelper::library()`.

That first call is also what defines the global `__()` and `___()` functions (in `LibraryHelpers/I18nHelper.php`). Until it happens they don't exist. `new I18n()` skips this step entirely.

---

## Configuration

`config/I18n.php`:

```php
return [
    // Text domain: the .mo file name. Default "messages".
    'domain' => 'messages',
    // Default language. Default "en".
    'lang' => 'en',
    // Available languages: code => title and locale.
    'langs' => [
        'en' => [
            'title' => 'English',
            'locale' => 'en_US',
        ],
        'it' => [
            'title' => 'Italiano',
            'locale' => 'it_IT',
        ],
    ],
];
```

The compiled translations go in `resources/translations/<locale>/LC_MESSAGES/<domain>.mo`. Italian with the default domain would be `resources/translations/it_IT/LC_MESSAGES/messages.mo`.

---

## Initialization

In your base controller constructor:

```php
// Default language from the configuration.
$this->i18n()->init($projectPath);
// Or a specific language.
$this->i18n()->init($projectPath, 'it');
```

`$projectPath` needs a trailing slash. `Config::string('APP_PATH_PROJECT')` already has one.

## Usage

### Language

```php
// Current language code: "it".
$lang = $this->i18n()->getLanguage();
// Current locale: "it_IT".
$locale = $this->i18n()->getLocale();
// The "langs" configuration.
$languages = $this->i18n()->getLanguages();

// Switch language. Throws an ApplicationException if it isn't in "langs".
$this->i18n()->setLanguage('en');
```

To remember a visitor's choice in the session and fall back to the browser language:

```php
$lang = $this->session()->get('lang', $this->request()->getAcceptLanguage());
if (!array_key_exists($lang, $this->i18n()->getLanguages())) {
    $lang = '';
}
$this->i18n()->init($projectPath, $lang);
```

### In source code

```php
$text = __('Hello');
// Plural.
$text = sprintf(___('%d file', '%d files', $count), $count);
// From another domain.
$text = __('Hello', 'emails');
```

### In views

```php
<?=__('Hello')?>
```

## Custom functionality

A module can bring its own translations. Switch to them, do the work, then switch back:

```php
$this->i18n()->setLanguage($lang, $customTranslationsPath);

// ...

// Back to the translations path from init(). The language stays the last one set.
$this->i18n()->reset();
```

---

## Notes

`LC_NUMERIC` is deliberately left alone. The locale is set for `LC_COLLATE`, `LC_CTYPE`, `LC_MONETARY`, `LC_TIME` and `LC_MESSAGES`, so `(string) 1.5` is still `"1.5"` in Italian or German and your SQL and JSON don't suddenly get decimal commas.

If `it_IT` isn't installed on the server, `setlocale()` gives up without an error and every text stays in the source language. Run `locale -a` on the server when translations mysteriously don't show.

gettext also caches `.mo` files per process. You updated a translation and nothing changed? Restart PHP-FPM or the web server.
